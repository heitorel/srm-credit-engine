# ADR-007 - AI-Assisted Development

## Status

Accepted

## Date

2026-07-07

## Context

The SRM Credit Engine technical challenge explicitly allows and encourages the use of Artificial Intelligence tools as development support.

However, the challenge also requires the author to maintain intellectual ownership of the delivered code and to document AI usage transparently.

The project must include an `AI_USAGE.md` file describing:

* strategic prompts used;
* where AI hallucinated or generated unsafe code;
* how unsafe or incorrect output was corrected;
* critical analysis of where AI saved time and where it caused risk.

The project will use **Specification-Driven Development** to reduce the risk of uncontrolled AI-generated implementation.

AI tools may support implementation, documentation, tests and review, but they must not replace engineering judgment.

## Decision

The project will use AI as a controlled engineering co-pilot.

AI-assisted development will follow these principles:

```text id="nx2iqo"
1. Specs before implementation.
2. Small scoped AI tasks.
3. Explicit files to read before each task.
4. Clear constraints and forbidden changes.
5. Tests required for business-critical logic.
6. Manual review before accepting generated output.
7. Continuous documentation in AI_USAGE.md.
```

The main AI tools considered for this project are:

```text id="di161t"
ChatGPT
Codex
```

Primary usage:

| Tool    | Planned Usage                                                                                |
| ------- | -------------------------------------------------------------------------------------------- |
| ChatGPT | Planning, risk analysis, specification drafting, architecture discussion, review             |
| Codex   | Scoped implementation, test generation, refactoring, debugging assistance, local code review |

AI output will always be treated as a draft.

The project author remains responsible for the final implementation.

## Rationale

### 1. AI can accelerate repetitive engineering work

AI tools can save time in areas such as:

* scaffolding;
* DTO generation;
* test case drafting;
* documentation drafting;
* refactoring suggestions;
* API examples;
* SQL review;
* frontend boilerplate.

These tasks are useful but must remain bounded.

### 2. Financial logic requires stricter control

The system handles financial calculations.

AI-generated code may incorrectly use:

```text id="4cltyz"
double
float
Double
Float
Math.pow
new BigDecimal(0.015)
```

or may apply currency conversion in the wrong order.

Therefore, AI-generated financial code must be reviewed against:

```text id="x2avq7"
docs/specs/03-business-rules.md
docs/adr/ADR-003-money-precision.md
```

### 3. Specification-Driven Development reduces hallucination risk

AI performs better when constrained by explicit context.

This project uses specification files, ADRs, diagrams and prompts to provide that context.

Each Codex task must reference the files that define the expected behavior.

### 4. AI usage transparency is part of the challenge

The challenge explicitly asks for AI usage documentation.

Keeping an active `AI_USAGE.md` file demonstrates:

* honesty;
* engineering ownership;
* critical review;
* ability to use AI productively without hiding behind it.

Examples:

* creating checklists.

### Documentation

Examples:

* drafting specs;
* drafting ADRs;
* drafting README sections;

### Implementation Support

Examples:

* generating Spring Boot scaffolding;
* generating Angular scaffolding;
* creating DTOs;
* creating basic controllers;
* creating mappers;
* creating repository skeletons;
* creating frontend components;
* creating form validation logic.

### Testing Support

Examples:

* suggesting unit test cases;
* generating test skeletons;
* creating edge case lists;
* writing integration test drafts;
* reviewing test gaps.

### Review and Refactoring

Examples:

* reviewing diffs;
* finding duplicated logic;
* identifying missing validations;
* suggesting better names;
* suggesting simpler structure;
* checking documentation drift.

## Forbidden AI Usage

AI must not be used to:

* generate the entire project in a single task;
* bypass understanding of the business rules;
* justify unsafe financial logic;
* accept floating-point financial calculations;
* hide assumptions;
* fabricate requirements;
* commit code that the author does not understand;
* skip tests because the code was generated by AI;
* leave generated code unreviewed;
* replace final ownership of the delivery.

## AI Ownership Rule

AI-generated output is not considered final until manually reviewed.

The author must be able to explain:

* what the code does;
* why the design was chosen;
* how financial calculations work;
* how transaction boundaries work;
* how errors are handled;
* how tests validate behavior;
* where AI helped;
* where AI was corrected.

The phrase "AI generated it" is not an acceptable explanation for a defect.

## Specification-Driven AI Workflow

Every AI-assisted implementation task should follow this workflow:

```text id="l4fzf0"
1. Identify the target feature.
2. Identify relevant specs.
3. Identify relevant ADRs.
4. Define allowed files/directories.
5. Define forbidden changes.
6. Define expected tests.
7. Ask AI for scoped output.
8. Review generated changes.
9. Run tests or checks.
10. Update AI_USAGE.md if the contribution was meaningful.
11. Commit with Conventional Commit message.
```

`AI_USAGE.md` must be updated when AI materially contributes to:

* project planning;
* architecture decisions;
* specification writing;

* test generation;

Small autocomplete-style suggestions do not need detailed logging unless they affect meaningful logic.

## AI Risk Areas

## 1. Financial Precision

### Risk

AI may generate financial code using binary floating-point arithmetic.

Unsafe examples:

```java id="qu0afi"
double presentValue = faceValue / Math.pow(1 + baseRate + spread, term);
```

```java id="j3q3xl"
BigDecimal spread = new BigDecimal(0.015);
```

### Required Review

Check that financial code uses:

```text id="qii10y"
BigDecimal
String-based BigDecimal constants
Explicit scale
Explicit rounding
```

## 2. Wrong Percentage Representation

### Risk

AI may represent `1.5%` as:

```text id="ctw7zy"
1.5
```

instead of:

```text id="d55ci2"
0.01500000
```

### Required Review

Check all rate examples, tests and seeds.

Correct values:

```text id="60df9h"
1.5% = 0.01500000
2.5% = 0.02500000
```

## 3. Wrong Currency Conversion Order

### Risk

AI may convert face value before discounting.

Incorrect:

```text id="5hlbi3"
Convert face value, then calculate present value.
```

Correct:

```text id="v3r8yi"
Calculate present value in source currency, then convert at the end.
```

### Required Review

Check pricing engine, settlement flow and tests.

## 4. Missing Exchange Rate Snapshot

### Risk

AI may incorrectly implement historical settlement views by reading the current exchange rate dynamically instead of using the persisted snapshot.

### Required Review

Settlement items must store the exchange-rate value used at settlement time.

Historical statement queries must read persisted values.

## 5. Partial Settlement Persistence

### Risk

AI may persist a settlement header before validating all items, causing partial records after failure.

### Required Review

Settlement creation must be transactional.

If any item fails, the entire operation must rollback.

## 6. Superficial Strategy Pattern

### Risk

AI may generate a large conditional block instead of Strategy Pattern.

Unsafe pattern:

```java id="6howqr"
if (type == MERCANTILE_DUPLICATE) {
    spread = ...
} else if (type == POST_DATED_CHECK) {
    spread = ...
}
```

### Required Review

Expected components:

```text id="p83svw"
PricingStrategy
MercantileDuplicatePricingStrategy
PostDatedCheckPricingStrategy
PricingStrategyResolver
```

## 7. In-Memory Reporting

### Risk

AI may implement settlement statement filtering by loading all rows into memory.

Unsafe pattern:

```text id="9f332w"
repository.findAll().stream().filter(...)
```

### Required Review

Reporting must use database-level filtering and server-side pagination.

## 8. Frontend Calculation Duplication

### Risk

AI may generate Angular code that implements the official pricing formula.

### Required Review

Frontend must call backend simulation endpoint.

Frontend may format values but must not own financial calculation.

## 9. Overengineering

### Risk

AI may suggest unnecessary architecture such as:

```text id="g4jwrg"
Kafka
Kubernetes
microservices
NgRx
distributed tracing
full CQRS
event sourcing
```

### Required Review

Initial delivery must prioritize Pleno-level requirements.

Advanced items may be documented as future improvements, not necessarily implemented.

## 10. Documentation Drift

### Risk

AI may change code without updating specs, ADRs or README.

### Required Review

Behavior changes must update documentation.

## Development Phase AI Strategy

## 1. Specification Phase

AI may help draft:

* README;
* AGENTS.md;
* AI_USAGE.md;
* specs;
* ADRs;
* diagrams;
* prompts.

Required review:

* verify consistency with challenge requirements;
* remove unsupported assumptions;
* mark assumptions clearly;
* ensure decisions are implementable.

## 2. Backend Scaffold Phase

AI may help create:

* Spring Boot project structure;
* Maven configuration;
* application configuration;
* Dockerfile;
* OpenAPI setup;
* global exception handler skeleton.

Required review:

* dependency versions;
* package structure;
* no premature business logic;
* configuration security.

## 3. Data Model Phase

AI may help create:

* Flyway migrations;
* seed data;
* JPA entities;
* repositories;
* constraints and indexes.

Required review:

* DECIMAL types;
* foreign keys;
* uniqueness constraints;
* audit columns;
* no Hibernate auto-DDL as final schema source.

## 4. Currency Engine Phase

AI may help create:

* exchange-rate endpoints;
* request/response DTOs;
* validation;
* repository methods;
* unit and integration tests.

Required review:

* source/target direction;
* positive rate validation;
* latest rate lookup;
* no implicit inversion unless documented.

## 5. Pricing Engine Phase

AI may help create:

* value objects;
* strategies;
* resolver;
* pricing engine;
* simulation endpoint;
* tests.

Required review:

* no floating-point types;
* correct spread values;
* correct formula;
* correct conversion order;
* explicit rounding;
* test coverage.

## 6. Settlement Flow Phase

AI may help create:

* settlement endpoint;
* transactional application service;
* settlement item persistence;
* audit snapshots;
* duplicate prevention tests.

Required review:

* transaction boundary;
* rollback behavior;
* status transitions;
* duplicate constraints;
* snapshot persistence.

## 7. Statement Query Phase

AI may help create:

* paginated query;
* filters;
* projections;
* indexes;
* tests.

Required review:

* database-level filtering;
* server-side pagination;
* deterministic sorting;
* no in-memory filtering.

## 8. Frontend Phase

AI may help create:

* Angular scaffold;
* Material components;
* reactive forms;
* API services;
* models;
* pages;
* loading and error states.

Required review:

* no financial formula in frontend;
* typed API integration;
* server-side pagination;
* clear error display.

## 9. Final Review Phase

AI may help review:

* README completeness;
* AI_USAGE completeness;
* spec/code consistency;
* delivery checklist;
* potential hidden defects.

Required review:

* manually verify every accepted suggestion;
* run tests;
* inspect Git history;
* ensure final branch and tag are correct.

## AI and Git Workflow

AI-assisted work must follow the Git workflow defined in:

```text id="l5njsb"
docs/adr/ADR-006-git-workflow.md
docs/specs/09-git-workflow.md
```

Rules:

* feature work must happen in feature branches;
* AI-generated changes must be reviewed before commit;
* commit messages must follow Conventional Commits;
* Pull Request descriptions must mention AI usage when material;
* `AI_USAGE.md` must be updated before merging AI-assisted features.

## AI and Testing

AI may generate tests, but generated tests must be reviewed.

Review generated tests for:

* meaningful assertions;
* no hardcoded incorrect values;
* no testing implementation details unnecessarily;
* correct financial expectations;
* cross-currency conversion order;
* failure scenarios;
* rollback behavior.

Do not accept tests that only verify that generated code behaves as generated.

Tests must validate business rules.

## AI and Documentation

AI may draft documentation, but documentation must match implementation.

Before final delivery:

* verify README setup commands;
* verify API examples;
* verify specs against code;
* verify ER diagram against migrations;
* verify C4 diagrams against architecture;
* verify AI_USAGE log;
* verify delivery checklist.

## AI and Security

AI-generated code must be reviewed for security issues.

Check for:

* committed secrets;
* unsafe CORS configuration;
* exposed stack traces;
* missing backend validation;
* SQL injection risk in dynamic queries;
* excessive logging of sensitive data;
* hardcoded credentials;
* unsafe Docker defaults.

## AI and Dependency Management

AI may suggest dependencies.

Before accepting a dependency:

* verify it is necessary;
* verify it is maintained;
* verify it fits the stack;
* avoid adding libraries for trivial tasks;
* prefer Spring Boot managed dependencies when possible;
* document major dependency choices if they affect architecture.

Do not accept dependencies only because AI suggested them.

## AI and Assumptions

AI must not silently introduce assumptions.

Examples of assumptions that must be explicit:

* term calculation convention;
* rounding mode;
* base rate source;
* exchange-rate direction;
* settlement status flow;
* batch size limit;
* frontend runtime configuration approach.

If an assumption is required, document it in:

```text id="ed17xn"
docs/specs/03-business-rules.md
```

or another relevant spec/ADR.

## AI Failure Handling

When AI generates incorrect, unsafe or irrelevant output:

1. reject the output;
2. identify the issue;
3. correct manually or ask for a constrained revision;
4. document meaningful failures in `AI_USAGE.md`;
5. add tests if the issue exposed a defect risk.

Examples that must be documented:

* AI generated `double` financial code;
* AI used wrong spread representation;
* AI converted currency in the wrong order;
* AI placed business logic in a controller;
* AI created in-memory report filtering;
* AI skipped error handling;
* AI suggested undocumented architecture changes.

## AI Usage Severity

AI issues may be classified as:

| Severity | Meaning                                                 |
| -------- | ------------------------------------------------------- |
| Low      | Minor wording, naming or formatting issue               |
| Medium   | Incorrect implementation detail with limited impact     |
| High     | Business rule, test or API behavior issue               |
| Critical | Financial, security, transaction or auditability defect |

Critical AI-generated defects must be documented if encountered.

## Required AI Evidence for Final Delivery

At final delivery, `AI_USAGE.md` must show:

* planning-stage AI usage;
* implementation-stage AI usage;
* at least one critical analysis section;
* any rejected or corrected AI output;
* how the author validated generated work;
* final ownership statement.

The final README should reference `AI_USAGE.md`.

## Consequences

### Positive Consequences

This decision provides:

* faster delivery;
* better planning support;
* improved test ideation;
* more complete documentation;
* controlled use of Codex;
* transparent AI usage;
* reduced risk of hidden generated assumptions.

### Negative Consequences

This decision adds:

* documentation overhead;
* need to maintain `AI_USAGE.md`;
* need to review AI diffs carefully;
* risk of overtrusting generated output;
* risk of broad AI-generated changes.

### Mitigations

Mitigations:

* use small scoped prompts;
* reference specs and ADRs;
* require tests for business-critical changes;
* keep `AGENTS.md` strict;
* review generated code before commit;
* reject unsafe financial logic;
* update `AI_USAGE.md` continuously;
* keep Git commits focused.

## Decision Validation

This ADR is valid if the final project demonstrates:

* `AI_USAGE.md` exists and is meaningful;
* AI usage is transparent;
* prompts are scoped and stored under `docs/prompts/`;
* generated code was reviewed;
* financial code avoids floating-point arithmetic;
* specs and ADRs guide implementation;
* PR descriptions mention material AI usage;
* tests validate business-critical logic;
* final ownership remains with the project author.
